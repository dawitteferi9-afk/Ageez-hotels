## In scope for v0.1
- Single fictional hotel (Ageez Grand Hotel) as seeded DB data
- Multi-tenant-ready architecture (hotelId on every tenant-owned record,
  centralized tenant-aware data access) even though only one tenant exists
- Guest checkout booking flow: Select Room (type) -> Dates + Guests + Guest
  Details (single form) -> Availability (checked server-side at submit,
  against real Reservation rows) -> Confirmation. No dedicated
  availability-search results screen — a guest picks a room type from
  Rooms & Suites first, then the form tells them if their dates work for
  it. Add-on services during checkout ("Extras") are out of scope for
  v0.1; post-booking service requests are covered by the ServiceRequest
  model (M4/M5 scope). See docs/DECISIONS.md for why this flow was chosen
  over a literal dates-first search.
- Simulated payment ("Pay at Hotel") — no real payment processing
- Management modules: Dashboard, Reservations, Rooms, Guests, Housekeeping,
  Maintenance, Services, Reports
- AI guest concierge grounded in approved hotel knowledge, no fabrication
- AI management assistant using whitelisted tool functions only
- Staff roles: OWNER/ADMIN, MANAGER, FRONT_DESK, HOUSEKEEPING, MAINTENANCE
- Reservations created on the website appearing in the management system

## Explicitly out of scope for v0.1
- Guest accounts / guest login (guest checkout only)
- Real payment processing
- Multiple live hotels (architecture supports it; only one is seeded)
- The full Hotel Generator / onboarding workflow (architecture must not
  block it later; it is not built now)
- Ageez platform-level administration UI (route boundary reserved only)
- Database-level Row-Level Security enforcement (app-layer tenant scoping
  now; RLS hardening is an M8 security review item, not redesign)
- Complex/full authentication features beyond Auth.js + the five staff roles

## M5 deliverables (complete)
Check-out, housekeeping, and maintenance — the operational half of the
Room lifecycle the M4/M5 boundary decision (`docs/DECISIONS.md`) deferred
out of check-in:
- **Check-out** (`withTenant().reservations.checkOut()`): `CHECKED_IN →
  CHECKED_OUT`, and derives the room's next state (`CLEANING` or
  `MAINTENANCE`) from whether an unresolved blocking `MaintenanceIssue`
  exists — never directly `AVAILABLE`. Check-in was also hardened to
  require the assigned room's status be `AVAILABLE` before allowing
  `CONFIRMED → CHECKED_IN`, now that `CLEANING`/`MAINTENANCE` are reachable
  states a same-day turnover could otherwise collide with.
- **Housekeeping** (`/management/housekeeping`,
  `withTenant().rooms.completeCleaning()`): a `CLEANING → AVAILABLE`
  workflow gated on OWNER_ADMIN/MANAGER/HOUSEKEEPING, re-verifying no
  unresolved blocking issue exists before allowing completion. No new
  housekeeping-task/assignment model — `Room.status` alone is the data
  model, per the approved M5 design.
- **Maintenance** (`/management/maintenance*`,
  `withTenant().maintenanceIssues.{report,manage}()`): every role may
  report an issue; only OWNER_ADMIN/MANAGER/MAINTENANCE may manage its
  lifecycle (assign, change status, add resolution/closure notes) against
  the approved status graph (`OPEN → IN_PROGRESS → RESOLVED/CLOSED`, with
  administrative closure requiring a reason). A blocking (`HIGH`/`URGENT`,
  unresolved) issue can take an `AVAILABLE`/`CLEANING` room to
  `MAINTENANCE`; resolving/closing the last one returns it to `CLEANING`,
  never directly `AVAILABLE`.
- Full Room state machine, the shared "blocking" definition, the
  maintenance status graph, and the `report`/`mutate` RBAC split are
  recorded in `docs/DECISIONS.md`'s 2026-08-26 M5 design-decisions entry
  and `docs/DATABASE.md`/`docs/SECURITY.md`. `RESERVED`/`OUT_OF_SERVICE`
  remain unused by every v0.1 write path. **No schema migration was needed
  for any M5 phase** — every model/enum M5 needed already existed from M1.
  Reports (occupancy/reservation/guest counts) remains the minimal,
  read-only M4-scoped snapshot — no new metrics were added for M5.
- **Verified end-to-end** against a live, seeded database: unit tests
  (pure domain validators + RBAC matrix), integration tests (`src/lib/tenant`
  against real Postgres, tenant isolation, atomicity), and Playwright e2e
  covering all three required lifecycle paths — normal turnover
  (check-in → check-out → housekeeping-complete), the blocking-maintenance
  variant (occupied stay with an unresolved blocker → check-out routes to
  `MAINTENANCE` → resolve → `CLEANING` → housekeeping-complete), and a
  cleaning interrupted by a newly-reported blocking issue. Exact commands/
  counts are in `docs/CHANGELOG.md`'s Phase d entry.

## M6 deliverables (Complete — Phases a+b+c+d+e)
The AI Guest Concierge's anonymous and verified tiers — no login required
for either; the verified tier requires proving ownership of one specific
reservation, per-conversation.
- **Provider abstraction + knowledge tools (Phase a, `2552a74`):**
  `src/lib/ai/provider.ts`'s vendor-neutral `AiProvider` interface,
  defaulting to a deterministic mock implementation unless
  `AI_PROVIDER=anthropic` is explicitly set; the real adapter
  (`src/lib/ai/providers/anthropic.ts`, `@anthropic-ai/sdk`); the two
  whitelisted anonymous-tier tools, `getHotelKnowledge()` (deterministic
  `AiKnowledgeDocument` lookup) and `getRoomTypesSummary()` (live
  `RoomType` data); and `buildAnonymousConciergeSystemPrompt()`. Library
  layer only — no route, no UI.
- **Anonymous public chat UI (Phase b, this checkpoint):** `/concierge` in
  the guest site, using the existing site layout/header/footer, with a
  hotel-named welcome message, four starter questions, and a
  `useActionState`-driven chat form. `sendConciergeMessageAction()`
  (`src/app/(guest)/concierge/actions.ts`) is the sole browser/AI boundary
  — it resolves the tenant, builds the system prompt, and calls
  `getAiProvider().converse()` with only the two-tool anonymous allow-list,
  returning nothing but a plain `{role, content}` transcript and a safe
  generic error string. Conversation history is browser-only React state
  — no persistence, no database table, no `localStorage`/`sessionStorage`.
  Grounded answers for policy/dining/facilities/room-type questions; an
  honest "I don't have that information" fallback for anything else,
  including live-availability and personal-reservation questions (the
  latter explicitly deferred to M6c, never faked). See
  `docs/DECISIONS.md`'s M6 design (recorded retroactively at this phase)
  and Phase b implementation-decisions entries, and `docs/AI_SPEC.md`.
- **Verified reservation/service-request context (Phase c, this
  checkpoint):** an optional booking-verification panel on `/concierge` —
  a guest supplies the displayed booking reference plus the email or
  phone used at booking; `withTenant().reservations.verifyGuestBooking()`
  narrows candidates by an indexed, tenant-scoped contact match and
  exact-compares the recomputed reference (never a suffix/`LIKE` lookup),
  resolving to exactly one reservation or failing generically (the
  Booking Verification Ambiguity Rule). Success issues a short-lived
  (30 min), HMAC-signed verified-context token
  (`src/lib/ai/verifiedContext.ts`) containing only `{hotelId,
  reservationId, guestId, exp}` — held in browser React state only, never
  a database table, never `localStorage`. Every guest-specific read
  (`getReservationSummary()`/`getServiceRequestStatus()`,
  `src/lib/ai/tools/verifiedConciergeTools.ts`) independently re-verifies
  that token's signature, expiry, current-tenant match, and a fresh
  tenant+guest-scoped database lookup before returning any data — a
  stale/expired/tampered/cross-tenant token fails safely and generically.
  `verifyReservationContextAction()` is rate-limited by an honest,
  explicitly demo/local-only in-memory limiter
  (`src/lib/ai/rateLimiter.ts`) — not production-grade for a scaled
  deployment, flagged as a future infrastructure requirement. Read-only at
  this phase: no ServiceRequest creation, no reservation change, no
  check-in/check-out is reachable at any verification level. See
  `docs/DECISIONS.md`'s M6c entries, `docs/SECURITY.md`'s "Verified guest
  context" section, and `docs/AI_SPEC.md`.
- **Confirmed guest ServiceRequest creation (Phase d, this checkpoint):**
  a verified guest may create ONE new `ServiceRequest` for their own
  reservation — the first guest-facing mutation, and the only one M6d
  adds. The model may only call `proposeServiceRequest` (non-mutating —
  no `@/lib/tenant`/Prisma import) to build a structured proposal, which
  the chat renders as a real confirmation card
  (`ServiceRequestProposalCard`, `src/components/guest/concierge-chat.tsx`)
  showing the exact guest-facing type/notes. Only an explicit "Confirm
  Request" button click submits the separate `confirmServiceRequestAction`
  Server Action — never in any AI tool registry, never invoked by a
  conversational "yes". That action independently re-verifies the token,
  revalidates the type/notes server-side, and calls the new
  `withTenant().serviceRequests.createForVerifiedGuest()` — structurally
  distinct from staff's `createForStaff()`, deriving `reservationId`/
  `guestId` only from the verified token. Uses the existing
  `ServiceRequestType` enum only — no schema migration. "Cancel" discards
  the proposal client-side, creating nothing. A verified guest can then
  read the new request's status through the existing, unchanged M6c
  `getServiceRequestStatus` tool. See `docs/DECISIONS.md`'s M6d entry,
  `docs/SECURITY.md`'s "Verified guest ServiceRequest creation" section,
  and `docs/AI_SPEC.md`.
- **Integration audit, final security review, and cross-milestone
  regression closeout (Phase e, this checkpoint):** no new guest
  capability — a verification-only pass tracing the six guest flows
  (anonymous knowledge -> booking verification -> verified read context ->
  ServiceRequest proposal -> ServiceRequest confirmation -> clear
  verification) as one integrated system, a final security audit
  (tenant isolation, ownership, token security, PII minimization, AI
  authority boundaries, server trust boundaries, secrets, rate limits,
  idempotency), and a full cross-phase regression run confirming M3/M4/M5
  are unaffected. No defect was found requiring a code change. Confirmed
  limitations, honestly documented rather than silently solved: rate
  limiting is in-memory/per-process (not distributed-safe), and
  `ServiceRequest` confirmation has no DB-level idempotency (a genuine
  duplicate double-submit can create two rows) — both explicit,
  deferred production-hardening items. See `docs/DECISIONS.md`'s M6e
  entry and `docs/CHANGELOG.md`'s Phase e entry for the full audit
  findings and exact test counts.
- Verified against a live, seeded database and the deterministic mock
  provider — exact commands/counts in `docs/CHANGELOG.md`'s Phase a,
  Phase b, Phase c, Phase d, and Phase e entries.
