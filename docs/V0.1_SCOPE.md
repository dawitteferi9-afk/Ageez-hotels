## In scope for v0.1
- Single fictional hotel (Ageez Grand Hotel) as seeded DB data
- Multi-tenant-ready architecture (hotelId on every tenant-owned record,
  centralized tenant-aware data access) even though only one tenant exists
- Guest checkout booking flow: Select Room (type) -> Dates + Guests + Guest
  Details (single form) -> Availability (checked server-side at submit,
  against real Reservation rows) -> Confirmation. No dedicated
  availability-search results screen — a guest picks a room type from
  Rooms & Suites first, then the form tells them if their dates work for
  it. Add-on services during checkout ("Extras") are out of scope for
  v0.1; post-booking service requests are covered by the ServiceRequest
  model (M4/M5 scope). See docs/DECISIONS.md for why this flow was chosen
  over a literal dates-first search.
- Simulated payment ("Pay at Hotel") — no real payment processing
- Management modules: Dashboard, Reservations, Rooms, Guests, Housekeeping,
  Maintenance, Services, Reports
- AI guest concierge grounded in approved hotel knowledge, no fabrication
- AI management assistant using whitelisted tool functions only
- Staff roles: OWNER/ADMIN, MANAGER, FRONT_DESK, HOUSEKEEPING, MAINTENANCE
- Reservations created on the website appearing in the management system

## Explicitly out of scope for v0.1
- Guest accounts / guest login (guest checkout only)
- Real payment processing
- Multiple live hotels (architecture supports it; only one is seeded)
- The full Hotel Generator / onboarding workflow (architecture must not
  block it later; it is not built now)
- Ageez platform-level administration UI (route boundary reserved only)
- Database-level Row-Level Security enforcement (app-layer tenant scoping
  now; RLS hardening is an M8 security review item, not redesign)
- Complex/full authentication features beyond Auth.js + the five staff roles

## M3 deliverables (complete)
Booking (`/rooms/[id]/book`) and Booking Confirmation
(`/booking/confirmation/[reservationId]`) — guest checkout only, no
accounts. Server Action (`createBookingAction`) validates dates/guest count/
contact details server-side, re-derives price and capacity from the
authoritative `RoomType` row, and checks real-time availability against
`Reservation` rows inside a Serializable transaction so two guests can't be
double-booked into the same room (`findAvailableRoom()` in
`src/lib/tenant`). Framework-agnostic booking rules (date validation,
night/price calculation, overlap detection, booking reference formatting)
live in `src/lib/domain/booking.ts`, unit-tested in
`tests/unit/booking.test.ts`. Adds `Reservation.guestCount` (migration
`20260824181030_add_reservation_guest_count`) and the `guests`/
`reservations` namespaces on `withTenant()`. First Playwright e2e coverage
(`tests/e2e/booking.spec.ts`, `playwright.config.ts`) exercises the full
guest journey plus two failure paths (invalid date range, exhausted
room-type inventory) against a live dev server and seeded database.
Select-room-first, no dedicated availability-search screen, no "Extras"
step — an explicit Product Owner decision; see `docs/DECISIONS.md`. See
`docs/CHANGELOG.md` for exact verification commands/results.

## M5 deliverables (complete)
**Note:** M4 (Management Dashboard) has no corresponding numbered
deliverables section here — a pre-existing documentation gap this pass did
not backfill, since it falls outside M5's own scope. M4's work is fully
described in `docs/CHANGELOG.md` and `docs/DECISIONS.md`.

Check-out, housekeeping, and maintenance — the operational half of the
Room lifecycle the M4/M5 boundary decision (`docs/DECISIONS.md`) deferred
out of check-in:
- **Check-out** (`withTenant().reservations.checkOut()`): `CHECKED_IN →
  CHECKED_OUT`, and derives the room's next state (`CLEANING` or
  `MAINTENANCE`) from whether an unresolved blocking `MaintenanceIssue`
  exists — never directly `AVAILABLE`. Check-in was also hardened to
  require the assigned room's status be `AVAILABLE` before allowing
  `CONFIRMED → CHECKED_IN`, now that `CLEANING`/`MAINTENANCE` are reachable
  states a same-day turnover could otherwise collide with.
- **Housekeeping** (`/management/housekeeping`,
  `withTenant().rooms.completeCleaning()`): a `CLEANING → AVAILABLE`
  workflow gated on OWNER_ADMIN/MANAGER/HOUSEKEEPING, re-verifying no
  unresolved blocking issue exists before allowing completion. No new
  housekeeping-task/assignment model — `Room.status` alone is the data
  model, per the approved M5 design.
- **Maintenance** (`/management/maintenance*`,
  `withTenant().maintenanceIssues.{report,manage}()`): every role may
  report an issue; only OWNER_ADMIN/MANAGER/MAINTENANCE may manage its
  lifecycle (assign, change status, add resolution/closure notes) against
  the approved status graph (`OPEN → IN_PROGRESS → RESOLVED/CLOSED`, with
  administrative closure requiring a reason). A blocking (`HIGH`/`URGENT`,
  unresolved) issue can take an `AVAILABLE`/`CLEANING` room to
  `MAINTENANCE`; resolving/closing the last one returns it to `CLEANING`,
  never directly `AVAILABLE`.
- Full Room state machine, the shared "blocking" definition, the
  maintenance status graph, and the `report`/`mutate` RBAC split are
  recorded in `docs/DECISIONS.md`'s 2026-08-26 M5 design-decisions entry
  and `docs/DATABASE.md`/`docs/SECURITY.md`. `RESERVED`/`OUT_OF_SERVICE`
  remain unused by every v0.1 write path. **No schema migration was needed
  for any M5 phase** — every model/enum M5 needed already existed from M1.
  Reports (occupancy/reservation/guest counts) remains the minimal,
  read-only M4-scoped snapshot — no new metrics were added for M5.
- **Verified end-to-end** against a live, seeded database: unit tests
  (pure domain validators + RBAC matrix), integration tests (`src/lib/tenant`
  against real Postgres, tenant isolation, atomicity), and Playwright e2e
  covering all three required lifecycle paths — normal turnover
  (check-in → check-out → housekeeping-complete), the blocking-maintenance
  variant (occupied stay with an unresolved blocker → check-out routes to
  `MAINTENANCE` → resolve → `CLEANING` → housekeeping-complete), and a
  cleaning interrupted by a newly-reported blocking issue. Exact commands/
  counts are in `docs/CHANGELOG.md`'s Phase d entry.
